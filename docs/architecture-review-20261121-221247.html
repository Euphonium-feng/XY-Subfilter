把浅模块变成深模块：字幕画布与 consumer 适配

扫描范围取自最近 40 个提交的热点：xy_sub_filter.cpp（13 次）、 hdmv_subtitle_provider.cpp（12 次）、 subtitle_display_layout（11+8 次）。 每个候选都只用 module / interface / depth / seam / adapter / leverage / locality 这套词汇描述。

37 个布局单测 13 个重采样单测 36 个 m_diag_* 成员 164 处诊断引用 53 处 display_area 读取

当前形状（问题所在）

同一决策，四处实现

“字幕画布用多大的显示尺寸”在 ReadBitmapCanvasInput、ResolveConsumerCanvas、LogHdrConfiguration、ResolveBitmapFrame 各自推导一遍，判据还互不相同。

同一身份，三种缓存

consumer 名称/家族被 provider（m_diag_consumer_name + 8 次重试）、wrapper（m_consumer_name + 8 次重试）、filter（m_xy_str_opt）分别缓存与分类。

发布几何，渲染与日志各算一遍

真正发布的 output/clip/offset 在 Render() 里分支决定，LogBitmapFrame() 又重新推导一份“published_*”，两者靠人工同步。

候选 01

CanvasRequest：把“显示尺寸 → 画布”收敛成一个深模块

Strong
FILES
  • src/subtitles/hdmv_subtitle_provider.cpp:23-63
  • src/subpic/XySubRenderProviderWrapper.cpp:15-76
  • src/filters/transform/vsfilter/xy_sub_filter.cpp:2242-2267
  • src/subpic/subtitle_display_layout.cpp:300-330
PROBLEM

四份实现读同一组选项，却给出不同的“可用性”判据：位图路径要求 fullscreen 两个方向都严格变大； wrapper 用 ContainsRect 且任一方向变大即可；日志又自己写了一套。 共享的 subtitle_display_layout 只拿到“已被解读过的输入”，所以真正的分歧留在调用方， locality 被破坏：想知道画布怎么算，必须同时读四个文件。

BEFORE · 四份策略，接口很浅
AFTER · 一个深模块，一个 seam
SOLUTION

新增 CanvasRequest::Resolve(const CanvasOptions&, const VideoGeometry&)： 输入是一个只含原始值的结构（显示尺寸、fullscreen、aspect、video rect），输出 CanvasPlan（画布矩形、是否启用、回退原因、采用的显示尺寸来源）。 读取 IXyOptions 的 adapter 只有一份，放在 seam 的这一侧；所有调用方只消费 CanvasPlan。

BENEFITS

locality：画布策略只在一个文件里。现在真有 37 个布局单测，但多数测的是“给定输入算几何”， 真正会分歧的“输入怎么来”没有测试面；seam 移到选项适配之后，这一层可以用假的 CanvasOptions 直接测。leverage：未来新增 consumer 只改 adapter，不动渲染。

候选 02

ConsumerIdentity：把“这是谁、要什么”变成一个模块

Strong
FILES
  • src/subpic/subtitle_display_layout.cpp:442-497
  • src/filters/transform/vsfilter/DirectVobSub.cpp:892-907
  • src/filters/transform/vsfilter/xy_sub_filter.cpp:808-827
  • src/subpic/XySubRenderProviderWrapper.cpp:364-405
  • src/subtitles/hdmv_subtitle_provider.cpp:175-242
PROBLEM

“consumer 是谁”被三套缓存各自持有，每套都带一个 8 帧重试循环；分类结果又在四处重新 ClassifyConsumer。最近一轮 isBitmap 反复，正是因为 “身份 / 呈现契约 / HDR 归属”这组知识没有单一归属：改一处，另一处仍按旧假设走。

BEFORE · 概念分散，接口重复
XySubFilter · m_xy_str_opt[name] → Classify → Contract
Wrapper2 · m_consumer_name + retries → Classify
HDMV provider · m_diag_consumer_name + retries → Classify
DirectVobSub · IsMpcVr / ConsumerOwnsHdr → Classify
3 caches · 3 retry loops · 5 classification sites
AFTER · 一套身份，一个契约
ConsumerIdentity { family, name, version }
ConsumerContract { overlay, singleBitmap, hdrOwner }
采样 / 缓存 / 重试：只在 identity 内
所有调用方拿同一个值对象
SOLUTION

把名称采样、限次重试、ClassifyConsumer、ResolveConsumerContract 收进一个 ConsumerIdentity 模块：构造时接收一个最小的“名称读取”函数指针， 之后只暴露 Identity() 与 Contract(canvas, isBitmap)。 三个缓存与三个重试循环删掉，改为各持有一个 ConsumerIdentity。

BENEFITS

删除测试通过：删掉三套缓存，复杂度集中到一处而不是转移。测试面从“构造 COM consumer”变成 “喂名称字符串”，于是 isBitmap 这类策略可以先用单测钉住语义，再谈实机。 locality 也回来了：想知道 MPCVR 为什么直通 HDR，只读一个文件。

候选 03

BitmapPublication：发布的几何只算一次

Worth exploring
FILES
  • src/subtitles/hdmv_subtitle_provider.cpp:848-900
  • src/subtitles/hdmv_subtitle_provider.cpp:509-529
  • src/subtitles/hdmv_subtitle_provider.cpp:531-553
PROBLEM

Render() 自己决定“MPCVR 单张画布”还是“madVR 分区”，而 LogBitmapFrame() 为了写日志，把同一组 published_output/clip/offset 再推导一遍。两处一旦不同步，日志会说“发布正常”而画面是坏的——这正是历史上多轮定位困难的形态。

BEFORE · 渲染与日志各算一遍
Render():
  if (prefer_single) { output = canvas; ... }
  else { output = m_canvas_publish_output; ... }
        ↓
LogBitmapFrame():
  published_output = prefer_single ? canvas : ...
  published_clip   = prefer_single ? canvas : ...
  published_offset = prefer_single ? 0 : ...
AFTER · 一个值对象，两处消费
BitmapPublication p = ResolvePublication(...);
Render(p);
LogBitmapFrame(p);   // 不再推导

struct BitmapPublication {
  enum Kind { Partitioned, SingleCanvas };
  Kind kind;
  RECT output, clip; POINT offset;
  RECT partitions[3]; int count;
};
SOLUTION

把“这次发布长什么样”抽成纯值对象 BitmapPublication，由纯函数从 画布 + 合同 + dirty rect 计算；渲染只负责按它发布，日志只负责序列化它。 去重比较也改为比较该值对象，删掉手写的 20 余项字段比较。

BENEFITS

seam 落在“算发布几何”与“发布 / 记录”之间，前者可以直接单测： madVR 分区、MPCVR 单张、画布关闭三种形态各一个用例。 leverage：第三个 consumer 到来时不必再改日志。

候选 04

BitmapFrameTrace：让诊断不再寄生在渲染状态里

Worth exploring
FILES
  • src/subtitles/hdmv_subtitle_provider.h:59-88
  • src/subtitles/hdmv_subtitle_provider.cpp:465-674
  • src/subpic/XySubRenderFrameWrapper.cpp:8-17
  • src/filters/transform/vsfilter/xy_sub_filter.cpp:58-67
PROBLEM

provider 里有 36 个 m_diag_* 成员、164 处引用；LogBitmapFrame() 做的是“20 多个字段逐一相等才早退”。诊断路径还与 Invalidate()、 Connect() 交错。日志文件路径函数在两处重复实现。 结果：改动渲染逻辑时很难判断哪些状态是“给日志的”，哪些是“渲染真的需要的”。

BEFORE · 状态与渲染混住
AFTER · 快照与去重集中
SOLUTION

引入 BitmapFrameTrace 值对象：由只读的 Snapshot(publication, stats, identity) 构造，自带 operator==；LogBitmapFrame() 只剩“变化则追加”。 m_diag_* 仅保留上一次快照一个成员。把重复的路径函数并入 diagnostic_log，并让 AppendXyDiagnostic 接受 wchar_t* 缓冲区以避免中间 CStringW 拼接。

BENEFITS

locality：日志字段与去重规则在同一文件； 渲染代码不再为了“让日志好看”而改变结构。测试面：快照可以直接构造并与字符串比对， 不必启动 provider。depth：接口从“36 个字段”收敛为“一个值”。

TOP RECOMMENDATION

先做候选 01（CanvasRequest），再做候选 02（ConsumerIdentity）

理由是可验证性，而不是“代码更整洁”：subtitle_display_layout 已有 37 个单测， 说明这层确实值得测，但真正出错的“输入怎么来”仍散在四处。把 seam 移到选项适配之后， 画布分歧第一次能在单测里复现——过去几轮“Auto/16:9 字幕消失”的排查正是卡在这里。 候选 02 紧随其后：它能把“consumer 语义”从实机试错变成可单测的策略表，最近一次 isBitmap 的反复就是缺少这块测试面的代价。

本报告未改动任何仓库文件。候选 03–05 在 01/02 落地后再评估；05 与既有 ABI 约束相关，默认不做。
